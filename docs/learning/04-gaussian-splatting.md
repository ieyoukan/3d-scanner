# 04. 3D Gaussian Splatting — 面を作らずに「見た目」を再現する

## このノートで分かること

- 3D Gaussian Splatting（3DGS）が、メッシュと何が違うのか。
- 「学習」とは何を最適化しているのか。なぜ SfM の結果が要るのか。
- OpenSplat の入力・出力・オプションと、CPU で動かすときの所要時間。
- PLY と SOG の違い。ブラウザでの表示のしくみ。

## 目的

メッシュ（[03](03-mvs.md)）は「形」を三角形で表す。形がはっきりした硬い物には向くが、
髪の毛、木の葉、ガラスの反射、空のような「面で表しにくいもの」は苦手。

3DGS は発想が違う。**形を求めようとせず、「どの角度から見ても写真と同じに見える」ことだけを目標にする。**
シーンを、大量の「半透明の色つきの粒」で埋め尽くす。

```text
メッシュ:  頂点と三角形。面の内側と外側がある。UV でテクスチャを貼る。
3DGS:      粒（ガウシアン）の集まり。面は無い。粒が重なって絵になる。
           → 3D プリントや物理演算には使えないが、見た目の再現は得意。
```

だからこのアプリでは、メッシュ（GLB）と 3DGS（PLY / SOG）を**別々の成果物**として扱う。
片方からもう片方は作らない。

## 入力

| 入力 | 場所 | 使われ方 |
| --- | --- | --- |
| 写真 | `images/` | 「正解の絵」。描画結果と比べる相手 |
| カメラの位置・向き・レンズ | `sparse/0/cameras.bin`、`images.bin` | 「どこから描画すれば、その写真と比べられるか」 |
| 疎な点群 | `sparse/0/points3D.bin` | 粒の初期位置と初期の色 |

OpenSplat は「プロジェクトのルート」を 1 つ受け取り、その直下の `images/` と `sparse/0/` を読む
（OpenSplat の `colmap.cpp` で確認。バイナリ形式のみ）。作業領域をこの形にしてあるのはそのため。

SfM の結果が必須な理由は 2 つ。カメラの位置が分からないと写真と比べられないこと。そして、粒を
でたらめな位置から始めると学習がうまく進まないこと（README に「ランダムな初期化は非対応」とある）。

対応するカメラモデルは SIMPLE_PINHOLE / PINHOLE / SIMPLE_RADIAL / OPENCV / FULL_OPENCV。
SfM で `SIMPLE_RADIAL` を指定しているのは、これに含まれるから。

## 処理

### 粒 1 つが持つもの

| パラメータ | 意味 |
| --- | --- |
| 位置 (x, y, z) | 粒の中心 |
| 大きさ（3 軸）と向き（四元数） | 楕円体の形。まとめて「共分散」と呼ぶ。細長い粒や平たい粒を表せる |
| 不透明度 | 0（透明）〜 1（不透明） |
| 色（球面調和係数） | **見る方向によって変わる色**。光沢や反射を表せる |

粒の濃さは、中心がいちばん濃く、離れるほど薄くなる（ガウス分布）。これが名前の由来。

### 学習 = 「描いて、比べて、直す」の繰り返し

```text
┌─→ 1. 写真を 1 枚選ぶ（そのカメラの位置と向きは SfM で分かっている）
│   2. いまの粒を、そのカメラから見た絵として描く
│        粒をカメラの画面に投影する（楕円体 → 楕円）
│        奥から手前へ並べ、半透明の絵の具のように重ね塗りする
│   3. 描いた絵と、本物の写真の差（損失）を計算する
│   4. 差が小さくなる方向に、全部の粒のパラメータを少しずつ動かす（勾配降下法）
│   5. ときどき、粒を増やしたり減らしたりする
│        足りない所: 粒を分割・複製する   ほぼ透明な粒: 消す
└── 6. 最初に戻る（これが 1 反復）
```

描画の計算がすべて「微分できる」式で書かれているので、「この粒をどちらに動かせば差が減るか」
（勾配）を自動で求められる。ニューラルネットワークの学習と同じ道具立てで、OpenSplat は
その計算に LibTorch（PyTorch の C++ 版）を使っている。

### 実行するコマンド

```bash
opensplat /data/scans/<id> -n 1000 -d 2 -o /data/scans/<id>/output/splat.ply --cpu
```

| オプション | 意味 |
| --- | --- |
| 第 1 引数 | プロジェクトのルート（`images/` と `sparse/0/` の親） |
| `-n` | 反復回数。OpenSplat の既定は 30000。README の動作確認例は 2000 |
| `-d` | 画像を 1/d に縮小して学習する。2 なら縦横半分（画素数 1/4） |
| `-o` | 出力先。**省略すると入力の隣に書かれる**ので、必ず指定している |
| `--cpu` | GPU を探さず CPU で実行する |

実装は `server/internal/reconstruction/pipeline.go` の `runSplat`。
スレッド数は環境変数 `OMP_NUM_THREADS` で伝える（LibTorch が OpenMP を使うため）。

### CPU で動かすということ

OpenSplat の README には「CPU でも動くが約 100 倍遅い」とある。GPU は CUDA / ROCm（AMD）/ Metal（Apple）に
対応していて、Intel の内蔵 GPU は対象外。配備先のクラスタには GPU が無いので、CPU で学習する。

実測（サンプル 11 枚、Apple Silicon 8 コアの Docker）:

| 学習時の解像度 | 反復回数 | 所要時間 | 1 反復あたり |
| --- | --- | --- | --- |
| 1416×1064（`-d 2`） | 300 | 7 分 23 秒 | 約 1.5 秒 |
| 1416×1064（`-d 2`） | 700 | 10 分 11 秒 | 約 0.9 秒 |

（同じ条件でも 1 反復あたりの時間に幅がある。同時に動いていた他の処理の影響と考えられる。）

所要時間は「反復回数 × 写真 1 枚の画素数」にほぼ比例する。写真の**枚数**は 1 反復の時間には
あまり効かない（1 反復で描くのは 1 枚だけ）が、枚数が多いほど必要な反復回数は増える。

見た目の変化（同じサンプルで確認）:

- 40 反復: 霧のかたまり。輪郭がかろうじて分かる程度。
- 700 反復: 窓・レンガの模様・屋根が判別できる。空や地面は大きくぼけた粒のまま。

このサンプルでは 700 反復まで粒の数が初期値（SfM の点数と同じ 8,359 個）のままだった。
粒を増やす処理（上の 5.）が効き始める前に終わっている。反復を増やせば細部は良くなるが、時間もかかる。
chart の既定は 1000 反復。**GPU 並みの品質を CPU で待つのは現実的でない**ので、
「まず見られる結果を出す」ための値にしてある。

### 進み具合の表示

OpenSplat は 1 反復ごとに `Step 123: 0.3098 [41%]` と出力する。サーバーはログの末尾からこれを読み、
「123 / 1000 ステップ」として API で返す（`server/internal/httpapi/progress.go`）。
作り物の数字ではなく、ツール自身が報告した値。

### 圧縮（SOG）

```bash
splat-transform -w -g cpu output/splat.ply output/scene.sog
```

3DGS の PLY は、粒 1 つにつき数十個の数値を生のまま並べたもので大きい。
SOG（Spatially Ordered Gaussians）は PlayCanvas の配信用形式で、各パラメータを 8 ビット程度に丸めて
WebP 画像に詰め、ZIP 1 ファイルにまとめる（不可逆圧縮）。公式の説明では PLY の 1/15〜1/20。

- `-w`: 出力ファイルがあれば上書き。
- `-g cpu`: 圧縮の中で唯一 GPU を使う処理（色の係数のクラスタリング）を CPU で行う。
  公式ドキュメントに「GPU が無くても動くが 5〜10 倍遅い」とある。実測では 1 秒だった（粒が少ないため）。

SOG への変換は独立したステップ（`sog`）にしてある。**これだけ失敗しても、PLY は登録済みなので表示できる**
（全体の状態は `partial` になり、ビューアは PLY を読み込む）。

## 出力

| ファイル | 内容 | 実測 |
| --- | --- | --- |
| `output/splat.ply` | 学習結果（粒の一覧） | 2.0MB（8,348 個） |
| `output/scene.sog` | 圧縮版 | 約 110KB |

成功の判定: PLY は先頭が `ply` で 1KB 以上、SOG は先頭が `PK`（ZIP の印）であることを確かめる。

### ブラウザでの表示

`web/src/viewer/SplatViewer.tsx`。PlayCanvas エンジンの `gsplat` コンポーネントを使う。
粒を毎フレーム奥から手前へ並べ替えて重ね塗りする処理は複雑なので、自作せず公式の実装に任せている。

注意点が 2 つある。

- PlayCanvas は **URL の拡張子**（`.sog` / `.ply`）で形式を見分ける（エンジンのソースで確認）。
  そのため成果物の URL は `/api/scans/<id>/assets/gaussian_sog/scene.sog` のようにファイル名で終わらせている。
- SfM の座標系は向きが任意。メッシュのビューアと同じ回転・平行移動（`web/src/viewer/sceneFrame.ts`）を
  掛けて、タブを切り替えても向きが揃うようにしている。

## よくある失敗

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| 全体がぼやけた霧のよう | 反復回数が少ない | `SPLAT_ITERATIONS` を増やす（時間は比例して増える） |
| 何時間も終わらない | CPU 学習で、反復回数や解像度が大きすぎる | 反復を減らす、`SPLAT_DOWNSCALE` を 4 にする（時間は約 1/4） |
| 「制限時間内に終わりませんでした」 | `SPLAT_TIMEOUT`（既定 6 時間）を超えた | 上と同じ |
| 「メモリ不足の可能性があります」 | メモリ上限を超えて強制終了された（`SIGKILL`） | 写真を減らす、縮小率を上げる、Pod のメモリ上限を上げる |
| 空中に色のついたもやが浮く | 写っている角度が少ない領域で、粒の位置が定まらない | いろいろな角度から撮り足す |
| 3DGS は出来たが粒が数十個しかない | SfM の点が少なすぎる（実機で 53 点の例を確認） | 撮り直して SfM の点を増やす |
| ビューアに何も出ない | URL に拡張子が無い、形式を取り違えている | アプリが返す `url` をそのまま使う |

## 確認方法

```bash
# 3DGS 分岐だけを、少ない反復で実行する
./scripts/fetch-sample.sh
docker run --rm --entrypoint /app/reconstruct -v "$PWD/samples/sceaux:/work" \
  -e ENABLE_MESH=false -e SPLAT_ITERATIONS=100 3d-scanner:dev -dir /work

# 学習の進み方（損失が下がっていく様子）を見る
grep '^Step' samples/sceaux/logs/splat.log | awk 'NR % 20 == 0'

# 粒の数を PLY のヘッダで確かめる（「element vertex N」の N が粒の数）
head -c 300 samples/sceaux/output/splat.ply | grep -a 'element vertex'

# SOG の中身（ZIP）を見る
unzip -l samples/sceaux/output/scene.sog
```

出来た `splat.ply` と `scene.sog` は、<https://superspl.at/editor> にドラッグして開くこともできる。

GPU での学習は**未検証**（[03-mvs.md](03-mvs.md) の「GPU を足したとき」を参照）。
