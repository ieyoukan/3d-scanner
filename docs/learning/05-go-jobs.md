# 05. Go のジョブ管理 — 数十分かかる処理を、落ちても迷子にしない

## このノートで分かること

- HTTP のリクエストと、数十分かかる処理をどう切り離すか（`202 Accepted` と待ち行列）。
- 状態（`queued` / `running` / `partial` …）がどこで、どういう規則で変わるか。
- 同じジョブを二重に実行しない仕組み（排他）。
- キャンセル、サーバーの再起動、保存期限の扱い。
- 外部 CLI を Go から安全に実行する方法。

## 目的

復元は数分から数時間かかる。HTTP の応答をそれまで待たせることはできない
（Cloudflare は約 2 分で接続を切る）。そこで:

1. アップロードを受け取ったら、**「受け付けた」とだけ答えてすぐ返す**（`202 Accepted`）。
2. 実際の処理は、裏で動くワーカーが順番に行う。
3. 画面は数秒おきに状態を問い合わせて表示する。

このとき難しいのは「途中で何かが起きたとき」。利用者がやめたくなった、サーバーが再起動した、
外部ツールが固まった。どの場合も、**状態が嘘をつかない**（処理していないのに「処理中」と表示し続けない、
失敗したのに「成功」と表示しない）ことを目標にしている。

## 入力

| 入力 | 場所 |
| --- | --- |
| 写真 | PVC の `/data/scans/<id>/images/` |
| ジョブの状態 | PostgreSQL の `scans` / `scan_steps` / `scan_assets` |

写真のような大きなデータは PVC に、状態のような小さく検索したいデータは DB に置く。

## 処理

### パッケージの分担

```text
server/
  cmd/server/main.go            起動と停止。部品を組み立てる
  internal/
    httpapi/         HTTP の入口。検証して下の層に渡すだけ
    jobs/            ワーカー、キャンセル、回復、掃除（このノートの主役）
    reconstruction/  外部 CLI を呼ぶ順番と、成果物の検証
    cmdrun/          外部 CLI の実行（タイムアウト、キャンセル、ログ）
    store/           DB への保存（PostgreSQL 実装と、テスト用のメモリ実装）
    scan/            状態の定義と、全体の状態を決める規則。何にも依存しない
    upload/          写真の検証と保存
    workspace/       PVC 上のパスの管理
    config/          環境変数の読み込みと検証
```

依存の向きは上から下への一方通行。`scan` は他のどれにも依存しないので、状態の規則だけを
単独でテストできる。

### 状態遷移

```text
                 ┌──────────────── 利用者が中止 ────────────────┐
                 │                      │                       v
  POST ──→ queued ──ワーカーが取る──→ running ──────────────→ cancelled
                 ^                      │
                 │                      ├─ 全部成功 ─────────→ succeeded
        再起動で中断                    ├─ 一部だけ成功 ─────→ partial
     （着手回数が上限未満）              └─ 見られる物が無い ─→ failed
                 │                      │
                 └──────────────────────┘

  どの状態からも、保存期限を過ぎると expired（ファイルを削除）
```

終わったときの状態は、ステップと成果物から 1 つの関数で決める（`server/internal/scan/scan.go` の `Summarize`）:

1. 見られる成果物（メッシュか 3DGS）が 1 つも無ければ `failed`。
2. 失敗したステップが無ければ `succeeded`（`skipped` は失敗に数えない）。
3. それ以外は `partial`。

規則 1 が最も大事。パイプラインが何も報告せずに正常終了しても（不具合や偽物でも）、
成果物が無ければ `failed` になる。「API は成功したが中身は空」を成功と呼ばないための歯止め。
この関数は入力と出力だけで決まる（DB も時計も使わない）ので、表形式のテストで全パターンを確かめている
（`scan_test.go`）。

### 待ち行列と排他

待ち行列の実体は DB の `scans` テーブル。専用のキューのソフトは使っていない。
ワーカーは次の 1 文で「いちばん古い `queued` を選んで `running` にする」（`store/postgres.go` の `ClaimNext`）:

```sql
UPDATE scans
SET status = 'running', started_at = $1, updated_at = $1, attempts = attempts + 1
WHERE id = (
    SELECT id FROM scans WHERE status = 'queued'
    ORDER BY created_at, id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
RETURNING ...
```

- 「選ぶ」と「`running` にする」が 1 文なので、間に割り込まれない。
- `FOR UPDATE SKIP LOCKED` は、他の誰かがロック中の行を**待たずに飛ばす**指定。
  2 つのワーカーが同時に実行しても、別々の行を取る。

MVP のワーカーは 1 つだけだが、この書き方ならワーカーを増やしても二重実行にならない。

### ワーカーのループ

`server/internal/jobs/service.go` の `Run`。

```text
繰り返す:
  ClaimNext で 1 件取る
    取れた → 実行して、すぐ次を見る
    無い   → 「合図」か「一定時間」を待つ
```

合図は容量 1 のチャネル。アップロードの受付が `Notify()` で鳴らす。容量を 1 にしてあるのは、
何度鳴らしても「起きろ」は 1 回で足りるから。合図を取りこぼしても、一定時間ごとに DB を見に行くので
ジョブが置き去りにならない。

同時実行は 1 件。理由は、SfM も 3DGS も全コアとメモリを使うこと、そして作業領域の PVC が
1 ノードからしかマウントできないこと（[06](06-helm-proxmox-csi.md)）。

### ジョブ 1 件の終わり方

`runJob` は、終わり方を 4 通りに分けている。

| 終わり方 | すること |
| --- | --- |
| 最後まで走った | ステップと成果物から全体の状態を決めて記録する |
| 利用者がキャンセルした | 状態は既に `cancelled`。ファイルを消す |
| サーバーが停止する | **何も記録しない**。`running` のまま残し、次の起動時に回復する |
| 記録しようとしたら `running` でなかった | 完了とキャンセルが同時に起きた。ファイルを消す |

### 「いまの状態が期待どおりのときだけ更新する」

状態を変える SQL には、必ず「いまの状態」の条件を付けている。たとえば完了の記録:

```sql
UPDATE scans SET status = $2, ... WHERE id = $1 AND status = 'running'
```

利用者のキャンセルと、ワーカーの完了がほぼ同時に起きたとする。キャンセルが先に `cancelled` にしていれば、
完了の `UPDATE` は条件に合わず何も変えない。**後から来た方が、先の結果を上書きしない。**
ロックを自分で管理しなくても、DB の 1 文の原子性だけで競合を防げる。

### キャンセル

`DELETE /api/scans/{id}` → `jobs.Service.Remove`。

```text
1. DB を cancelled にする（先にやる。以降、ワーカーの完了は無視される）
2. 実行中なら、そのジョブ専用の context を取り消す
     → cmdrun が外部プロセスに SIGTERM を送る
     → 5 秒待っても終わらなければ SIGKILL
3. ワーカーが、プロセスの終了を確認してから作業ディレクトリを消す
```

ファイルを消すのをワーカーに任せているのは、外部プロセスがまだ書いている最中に消すと、
プロセスがファイルを作り直して残骸になることがあるため。

### 再起動からの回復

Pod の再起動（デプロイ、ノードの再起動、メモリ不足）は処理の途中でも起きる。そのとき DB には
`running` の行が残るが、実行しているプロセスはもう居ない。放置すると画面は永久に「処理中」になる。

起動時に `Recover` が、`running` の行を見つけて片付ける（`store.RecoverInterrupted`）:

- 着手回数が上限（既定 2）未満 → `queued` に戻してやり直す。途中経過は消し、写真だけ残す。
- 上限に達した → `failed` にする。同じジョブがサーバーを落とし続けるのを止める。

この回復は「ワーカーは自分 1 つだけ」という前提に立っている。複数あると、他のワーカーが実行中の
行まで戻してしまう。chart がレプリカを 1 に固定しているのは、これを守るためでもある。

### 保存期限の掃除

`server/internal/jobs/janitor.go` の `Sweep`。10 分ごとに:

1. 期限を過ぎたスキャンのファイルを消し、状態を `expired` にする。
2. `expired` になってから十分経った行を消す。
3. DB に行が無いのに残っているディレクトリ（受付の途中で落ちた残骸）を消す。
   ただし 1 時間以上前のものだけ。受付中のディレクトリは、DB から見るとまだ存在しないスキャンに見えるため。

順番は「ファイルを消してから状態を変える」。途中で落ちても、状態が `expired` になっていなければ
次回もう一度処理される。逆順だと「`expired` なのにファイルが残っている」状態が二度と掃除されない。

### 外部 CLI の実行

`server/internal/cmdrun/cmdrun.go`。守っている決まりは 4 つ。

1. **シェルを通さない。** `exec.CommandContext(ctx, name, args...)` に、プログラム名と引数を別々の文字列で渡す。
   `sh -c "colmap ... " + path` のような文字列連結をしないので、引数に `;` や `$()` が紛れても、
   ただの文字として扱われる。
2. **必ず時間制限を付ける。** 固まった外部プロセスがワーカーを永久に塞がないように。
3. **キャンセルできる。** context が取り消されたら、プロセスグループごと止める。
4. **出力を全部ログに残す。** 実行したコマンド、標準出力・標準エラー、終了のしかたと所要時間。

プロセスグループを使うのは、CLI が内部で起動した孫プロセスまで確実に止めるため。
子プロセスを新しいグループのリーダーにしておき、`kill(-pid, sig)` でグループ全体にシグナルを送る。

失敗は種類を区別して返す: 起動できない／終了コードが 0 以外（`ExitError`）／時間切れ（`ErrTimeout`）／
取り消し。`ExitError` にはシグナルの名前も入る。`SIGKILL` はメモリ上限超過が典型、
`SIGABRT` はツール自身の異常終了で、利用者への説明が変わる。

## 出力

| 出力 | 場所 |
| --- | --- |
| スキャンとステップの状態、失敗理由 | `scans`、`scan_steps` |
| 成果物の目録（種類・相対パス・サイズ） | `scan_assets` |
| ステップごとの外部 CLI のログ | `/data/scans/<id>/logs/<step>.log` |
| サーバーのログ（JSON） | 標準出力 |

DB には相対パスだけを保存する。配信の直前に、作業ディレクトリの外を指していないかを確かめる
（`workspace.Resolve`。`..`、絶対パス、外を指すシンボリックリンクを拒否）。

## よくある失敗

実機で観測したもの:

| 症状 | 原因 | 対応 |
| --- | --- | --- |
| キャンセル後、数秒間プロセスが残っていた | COLMAP は SIGTERM では止まらなかった | 猶予を 10 秒から 5 秒に縮め、最後にグループごと SIGKILL する掃除を足した |
| 「メモリ不足」と表示されたが実際は違った | 終了コード -1 を一律に OOM と判定していた | シグナルの種類を記録して区別するようにした |
| 「終了コード 1」としか出ない | `mapper` が「モデルを作れなかった」とき 1 を返す | その出力を見つけたら、撮り直し方の説明に置き換える |
| 同じ写真 8 枚を送ると「写真が足りません」 | 完全に同じ写真は除かれる | 仕様どおり |

設計上、起きうるもの:

| 症状 | 原因 |
| --- | --- |
| 再起動のたびに同じジョブが落ちる | そのジョブがメモリ上限を超える。着手 2 回で `failed` になる |
| `queue_full`（429） | 順番待ちが上限（既定 5）に達している |
| `disk_full`（507） | PVC の空きが足りない。期限切れを待つか、容量を増やす |

## 確認方法

```bash
cd server
go vet ./...
go test -race ./...           # -race は goroutine 間の競合を実行時に検出する

# 読むとよいテスト
go test ./internal/scan/ -run Summarize -v           # 全体の状態の規則
go test ./internal/jobs/ -v                          # キャンセル、回復、掃除、1 件ずつの実行
go test ./internal/cmdrun/ -v                        # シェル非経由、時間切れ、孫プロセスの停止
go test ./internal/reconstruction/ -run Run -v       # 実行順、部分成功、成果物の検証

# 本物の PostgreSQL に対する契約テスト（専用の DB を指定すること。テーブルを空にする）
TEST_DATABASE_URL='postgres://user:pass@localhost:5432/scanner_test?sslmode=disable' \
  go test ./internal/store/ -run Postgres -v
```

動いているサーバーで確かめる:

```bash
# キャンセル: 投入してすぐ DELETE し、プロセスとディレクトリが消えることを見る
curl -X DELETE "$BASE/api/scans/$ID" -H "Authorization: Bearer $TOKEN"
docker compose exec app sh -c 'ls /data/scans'

# 回復: 処理中に再起動し、ログに「中断されていたジョブをやり直します」が出ることを見る
docker compose restart app && docker compose logs app | grep -E '中断|やり直'
```

どちらも Docker Compose 上で実際に確認した。Kubernetes でも、使い捨ての k3s（v1.33.6）に chart を入れ、
ジョブ実行中に `kubectl delete pod` して、新しい Pod が同じ PVC を引き継いでやり直すことを確認した。
本番クラスタ（Proxmox CSI）では**未検証**。

### テストの考え方

- `store` は PostgreSQL 実装とメモリ実装の 2 つがあり、**同じテストを両方に流す**（`contract_test.go`）。
  テスト用のメモリ実装が本番と違う動きをしたら、他のテストが通っても意味が無いため。
- `reconstruction` と `jobs` のテストは、偽の Runner や偽の Pipeline を使う。確かめているのは
  「順番」と「失敗したときの振る舞い」であって、3D 復元が正しいことではない。
  本物の実行結果は README の「検証の記録」にある。
